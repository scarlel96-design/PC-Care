# WO03 signed update package v2

`spd-update-v2` is a ZIP containing exactly `update.manifest.json`, `update.signature.json`, and the files listed in `Files`. JSON property names use the PascalCase spelling in `SignedManifest` and `SignatureEnvelope`; unknown and duplicate properties are rejected. The signature envelope contains a base64 `Signature` in IEEE P1363 fixed-field format (64 bytes).

The signed byte string is produced by `SignedPackage.CanonicalBytes`: a UTF-8 length-prefixed domain string `PC-CARE-SIGNED-UPDATE-V2\0`; then length-prefixed Format, Product, Publisher, KeyId, Algorithm, Channel, PackageId, FromVersion, ToVersion, MinimumSupportedVersion; then UTC ticks for CreatedAt and ExpiresAt as little-endian signed 64-bit integers; then file count as little-endian signed 32-bit integer; then each file sorted by ordinal Path, with length-prefixed Path, little-endian signed 64-bit Length, and length-prefixed lowercase SHA-256 hex. `BinaryWriter` uses little-endian numeric encoding. An ECDSA P-256/SHA-256 signature covers those bytes. The ZIP entry bytes are hashed separately and checked against the signed file list.

The verifier requires Product `PC-Care`, Algorithm `ECDSA-P256-SHA256-P1363`, Channel `stable`, a nonempty publisher and key ID, a nonzero 32-digit GUID PackageId, valid versions with `minimum <= current`, `from <= current < to`, and `CreatedAt <= now <= ExpiresAt`. It rejects undeclared or missing files, case-insensitive duplicate ZIP names, absolute/parent paths, Windows device names, link entries, oversized metadata, entries or package, and content-hash mismatches. It limits an entry to 512 MiB and the package to 2 GiB. The helper re-verifies the protected copy before extracting and rechecks staged hashes immediately before application.

The signed PackageId is stored in the committed transaction journal. A later application of the same PackageId is rejected as `REPLAY`, including when a caller incorrectly supplies the old installed version. Version monotonicity and package expiry provide additional replay bounds; retaining protected committed journals is required for the PackageId check.

The format is intentionally incompatible with legacy unsigned v1 packages. The legacy inspector can display content verification but its `CanApply` remains false. The existing `create-update-package.ps1` produces v1 only and must not be used to publish an in-app v2 update.

Algorithm choice: .NET 10 exposes ECDSA `VerifyData` with `DSASignatureFormat.IeeeP1363FixedFieldConcatenation`, which gives fixed-size signature framing and avoids DER parser ambiguity. RSA-PSS/SHA-256 is also supported but has larger keys and signatures. Neither algorithm substitutes for pinning the publisher's public key. References: [ECDSA VerifyData](https://learn.microsoft.com/en-gb/dotnet/api/system.security.cryptography.ecdsa.verifydata?view=net-10.0), [DSASignatureFormat](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dsasignatureformat?view=net-10.0).

Production trust currently contains no public key. Test keys are generated in the test process and injected only into test policies. Production activation awaits a separately managed official key and verified distribution of its public half.
